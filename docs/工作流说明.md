# 开发过程思路 & 工作流说明

## 一、我的开发流程

### 工具选择

- **Vibe Coding 工具**：Claude Code CLI
- **大模型**：DeepSeek V4 Pro / V4 Flash（通过 Anthropic 兼容端点接入）
- **为什么选这套组合**：
  - Claude Code 能直接读写项目文件、执行命令、跑测试，是"能动手"的工具，而不是浏览器里的对话框——这决定了它可以承载真正的工程化流程（不是复制粘贴代码）。
  - DeepSeek 对中文语义理解好，而本项目的核心产出是中文圆桌对话与中文 Prompt，中文质量直接决定产品体验；同时它兼容 Anthropic 协议，可以直接替换 Claude Code 的后端模型。
  - 分工：**我做决策（拆任务、定契约、审代码、判断取舍），AI 做执行（写代码、跑命令、补测试）**。每一轮迭代都是"我先定验收标准 → AI 实现 → 我审查 → 不达标就打回"。

### 整体思路

没有把需求整体丢给 AI 生成，而是按四个阶段切分，每个阶段都有明确的**产出物**和**验收标准**：

| 阶段 | 目标 | 产出物 | 验收标准 |
|------|------|--------|---------|
| SDD | 冻结数据模型与 API 契约 | Prisma schema、ER 图、API 文档、SSE 事件表 | 字段、状态、事件类型全部定型，后续不再改 |
| DDD | 页面与组件结构 | 路由、store、组件树 | 页面能用假数据跑通流转 |
| TDD | 核心业务逻辑 | 嘉宾生成、讨论编排、共识提炼 | 先写测试（红）→ 再实现（绿） |
| E2E | 系统级闭环 | Playwright 用例 | 关键用户旅程可自动化验证 |

实际执行时做过一次顺序微调：**讨论编排的 TDD 提前到了前端 DDD 之前**。理由很实际——编排是整个系统的数据源头，一旦它的输出契约不稳，前端做出来也要返工；而且它风险最高（依赖大模型的不确定性），应该尽早排雷。

### 每个阶段的推进方式

统一遵循"先设计、后实现"：

1. **先让 AI 分析现状**，而不是直接写代码。例如 SDD 阶段让它从五个维度分析模型不足，并给出"保守方案 / 完整方案"两套对比。
2. **我来拍板**，并把理由写进决策记录（本项目累计 17 条关键决策）。
3. **先写测试**，跑红，确认测试真的能抓住问题，再实现。
4. **实现后跑全量测试 + 类型检查**，两项都过才算完成。
5. **一个阶段一个 commit**，commit message 带阶段前缀（`feat(sdd)` / `feat(tdd)` / `fix(orchestrator)`），保证历史可回溯、可逐段 Review。

### 阶段性成果

- 后端单元测试 69 项、前端 reducer 测试 14 项、Playwright E2E 确定性用例 9 条，全部通过
- 真实联调：一场 4 专家讨论产生 870 条 SSE 事件、825 个 chunk、0 error

## 二、遇到的典型问题及解决路径

### 问题 1：Prisma 7 破坏性变更导致迁移失败

**问题描述：**
执行 `prisma migrate dev` 报错：`The datasource property 'url' is no longer supported in schema files`。项目是按 Prisma 6 风格写的（url 在 datasource 内 + CommonJS + ts-node-dev）。

**解决思路：**
让 AI 核实已安装版本（prisma@7.10.1），确认这是 Prisma 7 的破坏性变更：连接串移到 `prisma.config.ts`，运行时需要 driver adapter。于是有两条路：
- 迁移到 Prisma 7：需要引入 `better-sqlite3` 原生模块（Windows 上需要 node-gyp + VS Build Tools，编译风险高）、改 generator、改 PrismaClient 实例化方式。
- 降级到 Prisma 6：改一行依赖版本。

**最终方案：**
降级到 6.19.3。判断依据是**收益/风险比**：Prisma 7 的所有改动对 MVP 功能零收益，却引入一堆不确定性。工程决策的原则是"不为工具升级牺牲交付确定性"。

> 同一阶段还否决了 AI 的另一条建议：它提议把 String 状态字段改成 Prisma enum，但 **SQLite 连接器不支持 Prisma enum**，照做会让迁移直接失败。这让我确立了一条工作原则：**AI 的技术建议必须结合具体技术栈验证，不能直接照搬**。最终改为"String 字段 + Zod 写入校验 + 前端 union 类型"三层约束。

### 问题 2：讨论第 2 轮专家零发言（概率性 bug）

**问题描述：**
一场 2 专家 2 轮的讨论，第 2 轮主持人追问后没有任何专家回应，直接进入总结。数据库里第 2 轮 Round 正常创建与关闭、无任何 error，但专家消息为 0 条。

**解决思路：**
因为 Round 正常、无报错，说明循环确实执行到了选人环节，问题出在"选人结果为空"。用完全相同的 SELECT prompt 复现 3 次，发现**模型在"返回 UUID"和"返回专家姓名"之间随机摇摆**（3 次里有 1~2 次给名字）。

根因链：
1. 选人返回 `{"speakers":["周敏行","李维舟"]}`（名字）；
2. `applyGuardrails` 只认 UUID，名字全部被过滤 → 空数组；
3. 兜底逻辑只在"后半程 + 存在未发言专家"时生效，而 2 专家的第 2 轮两人都已发过言，条件不成立；
4. 本轮 0 发言，直接关轮进入总结。

**最终方案：**
1. 选人解析改为"ID 优先、姓名兜底"，并统一去重；
2. 每轮硬性保底 `min(2, 专家数)` 位发言人，不足时按已发言次数升序补，不再只在后半程生效；
3. **把"各专家已发言次数"真正写进选人 prompt**——此前 prompt 里写着"见下方"，但下方根本没有这个数据，公平性规则形同虚设；
4. 嘉宾生成时校验专家姓名唯一（否则"姓名→ID"映射会歧义），重名视为内容性错误并重试。

**更重要的收获是测试观**：原有 19 项测试全部 mock 合法 ID，所以从未覆盖"模型违约"的情况——**只 mock 正确数据等于没测**。修复时先补了 4 条会失败的回归用例（返回姓名 / 返回空数组 / 返回未知 ID / 第 1 轮就返回姓名），确认全红后才动代码。

### 问题 3：演播厅永久卡在"正在进入演播厅…"

**问题描述：**
点开某些讨论后页面全屏转圈，永不结束。加 8 秒超时也无效。

**解决思路：**
根因不是请求挂起，而是**状态映射语义混淆**：`phaseFromStatus('generating')` 返回了 `'loading'`，而 `loading` 的本意是"hydrate 中"。hydrate 其实早就成功了，但 phase 永远停在 loading，所以超时机制根本没机会触发。

**最终方案：**
1. 拆出独立的 `generating` 阶段，页面正常渲染"嘉宾生成中…"引导，不再全屏转圈；
2. `load()` 加 8 秒 `Promise.race` 超时，超时进入 error 态并给出重试按钮；
3. 同时修复一个交互缺陷：没有嘉宾阵容时，「开始讨论」按钮是 disabled 的，鼠标悬停只有禁止符号，**没有任何文字解释为什么不能点**。改为黄色引导条 + 「去生成嘉宾 →」按钮，把"沉默失败"变成"可执行的替代路径"。

### 问题 4：Windows 下 curl 传中文变乱码

**问题描述：**
联调时入库的 topic 是乱码，一度怀疑是服务端编码问题。

**解决思路：**
用 UTF-8 文件体 `--data-binary @utf8.json` 复测，topic 完整回读、无替换字符，证明服务端 UTF-8 链路正常。根因是 Git Bash 里内联 `-d '中文'` 按 GBK 发送。

**最终方案：**
把"HTTP 请求体必须是 UTF-8 JSON，Windows 下用文件体传中文"写进项目技术约束，避免重复踩坑。

### 附：一个自己发现的测量错误

LLM 冒烟测试最初报告"生成 1159 tokens 仅用 160ms"，明显不合理。排查发现计时点取在 `res.text()` 之前——`fetch()` 在响应头到达时就 resolve，所以只测到了首字节。修正后真实耗时 10~25 秒。**这个数字直接决定了架构决策**：正因为单次生成要十几秒，才必须给前端做 loading 态，而不是同步等 HTTP 返回。

## 三、我对"工程化 AI 开发"的理解

工程化 AI 开发的核心不是"让 AI 写更多代码"，而是**把 AI 的不确定性关进工程约束里**。AI 的价值在于执行速度和知识广度，它的风险在于"看起来很对"。这一路下来，凡是出问题的地方，都不是 AI 不会写代码，而是它写的东西"表面上能跑、实际不对"——比如只认 UUID 的选人逻辑在 mock 数据下永远通过，只在真实模型返回姓名时才暴露；比如 `generating` 映射成 `loading` 在类型上完全合法，只在真实点击时无限转圈。所以真正起作用的不是"更聪明的 prompt"，而是**契约、测试与验证闭环**：先把数据模型和接口冻结成契约，再用测试把契约钉死，最后用真实调用证伪所有假设。

另一个体会是：**人是决策者，不是审稿人**。整个过程里我否决过 AI 的 enum 建议（SQLite 不支持）、否掉了"嘉宾生成走 SSE"的方案（没有真实事件可推，只能推假进度）、也否掉了"E2E 真跑一场讨论"的做法（慢、贵、必 flaky）。这些判断都不需要我比 AI 更会写代码，只需要我知道"这个项目此刻最重要的是什么"。AI 能给出 90 分的代码，但"什么该做、什么不该做、什么时候停"必须由人来定——这也是我认为未来工程师的核心竞争力所在：不是写代码的速度，而是定义问题、验收标准和取舍边界的能力。
