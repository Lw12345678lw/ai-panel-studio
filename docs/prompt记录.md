# 核心 Prompt 记录文档

> 记录引导 AI 开发的最核心原始 Prompt，体现多范式的阶段性。
> 每段 Prompt 后附 1-2 句说明（当时意图、遇到了什么挑战、如何引导 AI 修正）。

---

## 阶段一：SDD 阶段 — 数据建模与 API 契约生成

### Prompt 1：五维度审视数据模型

```
不要急着写业务代码。我们先把 SDD 阶段做完：数据建模与 API 契约必须完全定型。
请基于 backend/prisma/schema.prisma 从 5 个维度分析当前设计的不足：
1. 讨论编排是否需要「轮次（Round）」实体？
2. 专家的「举手/抢答/准备发言」内部状态要不要持久化？
3. 多讨论并行时，状态隔离在数据库层如何保证？
4. ConsensusItem 是否需要追溯来源？
5. summary 和「最终共识」是不是同一个东西？
每问给判断+理由，并给保守方案（MVP）与完整方案（生产级）及优缺点。不要改代码，等我确认。
```

**说明：** 意图是让数据模型在写代码前经受结构化拷问。引导 AI 输出「保守/完整」两档方案供选择，最终拍板走保守方案（轻量 Round + 追溯 join 表 + 移除瞬态 status），避免过度建模。

### Prompt 2：定型契约并落地

```
确认按保守方案推进（5 项），但否决 String→Prisma enum（SQLite 不支持），
改用注释 + Zod + 前端 union 三层约束；同步移除 PanelMember.status，
运行时状态按 Map<discussionId, Map<memberId, RuntimeState>> 设计。
执行：改 schema → prisma migrate dev → 同步 ER图.md / API文档.md。
```

**说明：** 意图是契约「完全定型」并落到迁移与文档。过程中遇到 Prisma 7 移除 `datasource.url` 的破坏性变更（P1012），经用户拍板降级到 Prisma 6.19.3 才解除阻塞。

## 阶段二：DDD 阶段 — 前端组件与页面生成

### Prompt 3：设计演播厅页面布局

```
进入 DDD 阶段。先只做页面骨架和组件树，用假数据跑通流转，不要接真实接口。

演播厅布局约束：
- 三栏：左侧发言记录（独立滚动，自动跟随最新一条 / 用户手动上滑时暂停跟随）、
  右上嘉宾席、右下共识与分歧；
- 顶部固定：话题标题 + 专家人数 + 状态胶囊；
- 状态分为 待开始 / 嘉宾生成中 / 直播中 / 已结束 四种，每种都要有明确的可视表达；
- 任何状态都不允许出现「永久全屏 loading」，必须有超时兜底和可重试的出口；
- 小于 768px 折叠为上下结构，三栏改纵向排列。

先输出组件树 + 状态映射表，说明每个状态由哪个字段驱动，我确认后再写代码。
```

**说明：** 意图是先把骨架和状态机定清楚，再往里填数据，避免接口一接就返工。这里踩了一个真实坑：最初把 `generating` 映射成了 `loading` 阶段，而 `loading` 的本意是「首屏数据加载中」，结果阵容未生成的讨论永远停在转圈状态，8 秒超时判断根本没机会执行。后来拆出独立的 `generating` 阶段，页面正常渲染引导条和「去生成嘉宾 →」按钮，卡死问题才真正解决——**状态映射的语义必须一一对应，不能复用**。

### Prompt 4：实现嘉宾小窗组件

```
实现嘉宾小窗 PanelSeat，单个座位包含：头像（取姓名首字 + 专属颜色）、姓名、
角色徽章（主持 / 嘉宾）、头衔、右侧当前状态。

状态只有三种：idle（静听）/ preparing（准备发言）/ speaking（发言中）。要求：
- 状态完全由 SSE 推送决定，组件内不许自行推断或定时器模拟；
- 同一时刻最多一个 speaking，其余必须回到 idle；
- 流式文字不进小窗，只在发言记录里逐字出现，小窗只负责「谁在说」；
- 所有关键元素补 data-testid，后续 E2E 直接断言，避免依赖文案选择器。
```

**说明：** 关键决策是**状态不落库**——`idle / preparing / speaking` 是高频瞬态，只存在内存并随 SSE 下发，避免数据库与内存两个真相源。同时把「流式文本」和「发言人状态」拆到两个组件承载：文字进 transcript，状态进座位卡，两者各自可独立测试。补 `data-testid` 是为 E2E 铺路，后来 9 条用例全部依赖它，没有一条用文案匹配。

## 阶段三：TDD 阶段 — 核心逻辑的测试用例编写与业务实现

### Prompt 5：嘉宾生成功能 TDD

```
先写测试 backend/tests/panelService.test.ts（mock 所有 API，绝不真实调用 DeepSeek）：
- 正常：话题 + 4 人 → 1 host + 4 expert，6 字段齐全，颜色合法且互不重复
- 边界：2 人、8 人
- 异常：非 JSON → 触发重试，重试仍失败抛自定义错误；超时 → 明确错误
先跑测试确认全红，我确认后再写实现（llm.ts 通用封装 + panelService.ts 校验）。
补 6 条脏数据测试：缺 stance / host 数量 0 或 2 / 专家数不符 / color 非法 /
name 空白 / 颜色重复（重复自动修复）。
```

**说明：** 意图是先固化契约再实现，强制 mock 杜绝真实调用。过程中纠正了一个计时 bug——`fetch()` 在响应头到达即 resolve，真实完整耗时须在 `await res.text()` 读完 body 后计时。用户追加「立场多样性」硬要求（覆盖争议维度、禁止中立套话、主持人中立），写入 system prompt。

### Prompt 6：讨论编排器 TDD

```
进入讨论编排模块，先设计、我确认后再写代码。输出编排设计方案：主持人调度策略、
专家发言选择、轮次节奏、上下文管理、SSE 事件映射。
确认后写 orchestrator.ts（runDiscussion + 固定状态机），先写测试再实现，mock 所有 LLM：
轮数驱动 / 选人护栏 / 共识提炼 + join / SSE 事件 / LLM 失败重试 / 超时优雅结束。
```

**说明：** 意图是核心编排先设计后实现。过程中用户追加多条 prompt 硬约束：专家必须点名回应他人观点、选人同轮不重复、共识必须带 `sources`（自然语言摘要）并反向匹配回本轮 Message 做溯源 join。

## 阶段四：E2E 阶段 — 系统级端到端测试与质量闭环

### Prompt 7：端到端测试

```
进入 E2E 阶段。有一个关键约束必须先定：

⚠️ E2E 绝对不要真的调用 LLM 跑一场讨论。
理由：一场 4 专家讨论 2~4 分钟 + 花钱 + 结果不确定，测试必然又慢又 flaky。
E2E 只覆盖确定性路径，真实全链路用 @slow 标记、默认跳过。

默认用例（基于 seed 数据，全部只读浏览）：
首页 5 条列表与状态徽章 / finished 讨论的发言与共识与总结 /
ongoing 显示直播中 / generating 不卡全屏 loading / waiting 的开始按钮可用 /
刷新后内容仍在 / 不存在的 id 显示错误页。

@slow 用例（默认 skip）：新建 → 生成阵容 → 开始讨论 → 等到结束，
断言 transcript 非空、总结出现；结束后清理自己创建的 [E2E] 讨论。
```

**说明：** 这条 Prompt 的核心是"先把测试边界划清"——如果不提前约束，AI 会倾向于写"看起来完整"的真实链路 E2E，结果测试跑 20 分钟还经常因模型输出差异而失败。实际执行中，9 条确定性用例 8 秒跑完且零成本；`@slow` 用例另用 `test.slow()` + 独立超时 + `afterAll` 清理。

另外为了降低选择器脆性，让 AI 统一给关键元素补 `data-testid`（讨论卡片 / 状态徽章 / 状态胶囊 / 嘉宾卡 / 发言项 / 共识项 / 总结 / 引导条）；并给 vitest 限定 `tests/**`，避免它误收集 Playwright 的 spec 文件。
